# Interface language

The application's own text is French or English, at the user's choice (spec 010). It is a
different thing from the **course language** ([course-language.md](./course-language.md), spec 011):
Célestin's speech, the board, the pack and the notation follow the course (French or English, fixed when
it is created), and **nothing the model reads ever depends on the interface language**.

| | Interface language | Course language |
|---|---|---|
| What | buttons, menus, labels, page titles, form messages, accessibility text, the errors, statuses, labels and markers the server writes for the student | Célestin's messages, the board's cards and drawings, chapter titles and sections, the pack, the transcription, the notation (`12,5 %`, `]a ; b[`), what is sent to the model |
| Who decides | the user (`users.locale`) | the course (`courses.language`) |
| Marked in the page | `<html lang>` | `lang="fr"` or `lang="en"` on the elements that show it (`useCourseLanguage()`, `lib/course-language.tsx`) |

## Which language, when

| Situation | Language |
|---|---|
| Signed out (sign-in, registration, error pages) | the first supported language of the browser's `Accept-Language`, `fr` if none |
| Registering | the language the visitor was reading is stored on the account (no field in the form) |
| Signed in | `users.locale`, whatever the browser says |
| Signing out | back to the browser's language |
| A session that died | the language stays until the redirect to sign-in (so a lesson on screen is not remounted), then the browser's |
| Changing it | « Paramètres » → « Langue »: saved to the account, applied at once, no reload |

Existing accounts read `fr` (migration `0006`). There is no cookie and no locale in the URL.

`Accept-Language` is read by one rule on both sides, pinned by one case table
(`backend/tests/fixtures/accept_language_cases.json` ↔
`frontend/src/lib/__tests__/accept_language_cases.json`): quality order then position, matched on
the primary subtag (`fr-BE` is `fr`), unsupported or malformed entries skipped, `fr` if nothing
matches. The page and the API therefore agree on the same header.

## Frontend

Paraglide JS compiles `messages/fr.json` (the base) and `messages/en.json` into typed message
functions in `src/paraglide/` (generated, gitignored; the Vite plugin writes it on `dev` and
`build`, `npm run i18n` elsewhere). Both languages ship in the one build.

| File | Role |
|---|---|
| `project.inlang/settings.json` | locales, and the message-format plugin loaded from `node_modules` |
| `src/lib/locale.ts` | `Locale`, `parseAcceptLanguage`, `matchLocale`: pure, shared by the error page |
| `src/lib/i18n.ts` | the two strategies (`custom-account`: the user in the `me` cache, else `<html lang>`; `custom-header`: the request's `Accept-Language` on the server), `useLocale`, `resetLocale` |
| `src/lib/html-headers.ts` | `Vary: Accept-Language` and `Cache-Control: private, no-cache` on HTML (see below) |
| `src/server.ts`, `src/start.ts` | `paraglideMiddleware` around the render (per-request language); the failed-render page in the browser's language |
| `src/components/celestin/locale-boundary.tsx` | remounts the tree when the language changes |
| `src/components/celestin/user-menu.tsx`, `settings/` | the menu, and the settings screen: a list of sections registered in `settings/sections.ts` |
| `src/lib/tutor/prompts.ts` | the sentences the interface sends to the model for the learner: French, never translated |
| `src/lib/i18n-format.ts` | interface numbers and sizes (`fr-BE` / `en-GB`); the board's notation stays in `charts/format.ts` |

Writing interface text:

1. `import { m } from "@/paraglide/messages"` and call `m.some_key({ name })` **inside a function**.
   Never at module scope: it would run once, outside the request, and freeze the language (a lint
   rule forbids it). A module-level table holds message *functions*: `{ done: m.state_done }`,
   read as `STATE_LABEL[s]()`.
2. Keys are flat `snake_case` with an area prefix (`auth_`, `course_`, `chapter_`, `content_`,
   `lesson_`, `voice_`, `board_`, `describe_*`, `settings_`, `nav_`, `error_`). Add the key to
   **both** files; `npm run i18n:check` (run by `npm test`) fails on a missing or extra key or a
   `{variable}` that differs.
3. Plurals use the inlang selector form, and French counts 0 and 1 as singular:
   `"x": [{ "declarations": ["input count", "local countPlural = count: plural"], "selectors": ["countPlural"], "match": { "countPlural=one": "{count} chapitre", "countPlural=other": "{count} chapitres" } }]`.
   Never build a sentence from fragments.
4. Zod schemas are factories called in render (`useMemo(makeSchema, [])`), not module constants.
5. Accessibility text (`aria-label`, `title`, the sr-only descriptions of the drawings) is interface
   text. The notation inside it still comes from `charts/format.ts`.
6. What follows the course, not the interface: `lib/tutor/prompts.ts` (the sentences sent to the model
   for the learner), the board's notation and vocabulary (`charts/format.ts`, `useNotation()`),
   anything the server sent (shown as received), Célestin's cards. Mark course text with
   `lang={language}` from `useCourseLanguage()`.

Guards: two ESLint rules (`eslint-rules/i18n.js`, pinned by `lib/__tests__/lint-rules.test.ts`)
flag an accented literal outside a short allowlist and a message call at module scope; the
**English sweep** (`src/test/english-sweep.ts`, which also knows a short list of unaccented French words, as whole words, used by `routes/__tests__/english-sweep.test.tsx`,
`lesson-sweep.test.tsx` and `components/celestin/__tests__/discussion-sweep.test.tsx`) renders every
screen in English and fails on accented French outside a `lang="fr"` region. Tests pin the
language to French (`src/test/setup.ts`) so the whole suite still reads as it always did;
`withLocale("en", fn)` (`src/test/locale.ts`) runs an English body.

## The product's name

« Célestin » is not translated and not in the catalog: `APP_NAME` in `src/lib/brand.ts` is what the app bar, the sign-in and registration cards and the document head read. The catalog strings that mention the tutor spell it out, in both languages. Its accent is the one accent the English checks allow: the English sweep (`src/test/english-sweep.ts`) ignores `APP_NAME`, and `test_an_english_file_carries_no_french` ignores the name in the English prompt files.

## Backend

| File | Role |
|---|---|
| `app/domain/locale.py` | `Locale`, `parse_accept_language` |
| `app/domain/messages/` | the catalog: `fr.py` (the text the code always said), `en.py`, `render`, `render_issue` |
| `app/domain/marker.py` | `Marker`: a `str` (the French label) that remembers its key and can say itself in another language |
| `app/api/locale.py` | `locale_of(request)`: the account's language (left on `request.state` by `current_user`), else `Accept-Language` |

An error holds a key (its code) and parameters; `TutorError.message(locale)` renders it, and the
wire shape `{code, message}` is unchanged. The HTTP handler, the two middlewares, the SSE `error`
event, the voice routes and the DTOs render with the request's language. Subject labels,
`« Chapitre N — »`, the failure messages of a preparation and the transcript markers
(`event_of(outcome, locale)`, `marker_for(..., locale)`) do the same. A `ContentIssue` has an
optional `code`: the student's editor shows `issue.<code>` in their language, the authoring model
keeps reading the French `message`. Plurals are `key.one` / `key.other` with a `count` parameter.

French stayed byte-identical: `tests/fixtures/error_messages_fr.json`, `status_messages_fr.json` and
`markers_fr.json` were recorded from the code before the catalog existed and are asserted against it.
`tests/unit/test_messages.py` pins parity (same keys, same `{fields}`).

### The wall around the model

`prompts/`, the tool declarations, tool outputs and `ToolValidationError` text, the history mapping
and `curriculum_render` take no interface `locale` and do not import the catalog. They do take the
**course language** (spec 011): the model path reads `ctx.language` / `chapter.language`, never
`locale`. `tests/unit/test_model_input_wall.py` checks the imports, that no model-facing module
names `locale` (the context only carries it for the events it emits, and `tutor_service` passes it
to `event_of`), and the behaviour: an `fr` and an `en` account on the same course hand the provider
byte-identical input; a French course and an English course hand it different input, each equal to
its own pinned rendering. So the cached prefix, the render goldens and the voice session depend on
the course and on nothing else the student chose.

## Hosting note

HTML pages depend on `Accept-Language` (the sign-in and registration pages are server-rendered).
AWS Amplify's CloudFront respects the app's `Cache-Control` for dynamic routes and has no
`Accept-Language` in its cache key, so `src/server.ts` sends `Cache-Control: private, no-cache` and
`Vary: Accept-Language` on every HTML response. Authenticated routes are client-rendered
(`ssr: false`), so nothing else is lost.

## Adding things

- **A string**: both `messages/*.json`, then `m.key()`. **A server message**: both
  `app/domain/messages/*.py` (`test_messages.py` fails on a mismatch).
- **A new error class**: its `code` is its catalog key; give it `params`, add the row to
  `tests/fixtures/error_messages_fr.json` with `make`. **A marker**: `Marker("marker.x")` and a key in both catalogs.
- **A settings section**: a component, its messages, one entry in `settings/sections.ts`. Changes that
  need proof of identity (email, password) get routes of their own, not fields on `PATCH /api/auth/me`.
- **A third language**: a catalog file per side, an entry in `LOCALES` (both) and `project.inlang`, the
  autonym. No component or error class names a language.

## Known gaps

- The two middlewares (same-origin and body size) run before authentication, so their refusals follow the browser's `Accept-Language` even for a signed-in user. The upload-size case is also checked in the browser.
- Opening the settings from a lesson is an ordinary navigation: the open turn is aborted, a voice session is stopped, the parcours transcript (in memory only) is lost, progress is not.

- A `ContentIssue` from a producer without a code (pydantic's own field messages, the transcription and
  agent issues) shows its French or pydantic English `message`; `test_issue_messages.py` pins the list.
- Sentences that mix interface wording with a course string (« Done when: … », « 2 exercises based on: … »)
  carry no `lang` for the course part.
- The server-rendered shell of an authenticated page is in the browser's language until the account's
  replaces it (`_auth` is `ssr: false`).
- The lint rule cannot see unaccented French; the English sweep only knows a short word list. Review does.

## Manual checklist

1. A browser set to English: `/login` and `/register` are English, `<html lang="en">`; set to French or
   another language: French.
2. Register: the menu reads « Settings » / « Paramètres » by the browser's language; « Paramètres » shows
   the language, nothing else.
3. Switch language: the page and the document title change at once; a reload keeps it; on another browser
   the same account opens in the same language.
4. Sign out: the sign-in page follows the browser again.
5. A course, a chapter in preparation, a refused upload, a refused pack edit, a lesson with a drawing, a
   discussion, a voice session: no French chrome in English, Célestin and the board still French.
6. At 400 px wide, with the longer language everywhere.
7. `curl -si -H 'Accept-Language: en-GB' https://…/login` and again with `fr-BE`: each answers in its own
   language with `Vary: Accept-Language` and `Cache-Control: private, no-cache`.
