# CLAUDE.md — backend

Guidance for Claude Code working inside `backend/`. Repo-wide context is in the root `CLAUDE.md`; the product brief is `../specs/product.md`; the feature specs are `../specs/001-tutor-chat-agent/` (the turn pipeline), `../specs/002-chapter-sections/` (the curriculum and the locked path), `../specs/004-accounts-and-classes/` (accounts, progress), `../specs/005-student-authored-courses/` (courses in the database, the authoring agent, prompt layers) `../specs/006-document-upload/` (PDF and photo uploads, the transcription stage), `../specs/007-discussion-mode/` (the second mode and stored conversations), `../specs/008-board-charts/` (charts on the board) and `../specs/009-board-drawings/` (flowcharts, figures and plots: no SDD trio, the reviewed designs per block and their deviations) and `../specs/010-interface-language/` (French and English interface: `users.locale`, the message catalog) and `../specs/011-course-language/` (French and English courses: `courses.language`, the English prompt set, per-language tables) and `../specs/012-admin-and-registration-modes/` (`users.enabled`, `REGISTRATION_MODE`, the admin role and its routes; no SDD trio).

## Commands

Run from `backend/`. Managed with `uv`; Python ≥3.12.

```sh
uv sync                                              # install
uv run alembic upgrade head                          # the schema; required before the first run
uv run uvicorn app.main:create_app --factory --reload --port 8000
uv run python -m scripts.seed --email e@x.be --password '…'   # a local student with chapter 1, no model call (--language en: the English fixture)
uv run python -m scripts.create_admin --email a@x.be --password '…'   # the only way to get an admin (spec 012); also recovers a lost admin password
uv run pytest                                        # full suite
uv run pytest tests/unit/test_config.py -q           # one file
uv run pytest -k history                             # one pattern
uv run python -m app.services.tools.dump_schema      # what the model sees, per mode
uv run python -m scripts.smoke                       # two real turns per mode; fails on a cache miss
uv run python -m scripts.probe                       # the guardrail probes, both modes
uv run python -m scripts.probe --charts              # chart probes (008), on the statistics fixture chapter
uv run python -m scripts.probe --flowcharts          # flowchart probes, on chapter 1
uv run python -m scripts.probe --figures             # figure probes, on the geometry, inequations and statistics fixtures
uv run python -m scripts.probe --plots               # plot probes, on chapter 1 and the MRU fixture (sciences)
uv run python -m scripts.voice_smoke                 # mints one real Realtime client secret
uv run python -m scripts.voice_probe                 # spoken-maths phrasing under the voice block
uv run python -m scripts.authoring_eval              # the real authoring agent on tests/fixtures/material; outputs in .eval/
uv run python -m scripts.document_eval --pdf path/to/course.pdf   # transcription + authoring on a document; .eval/document/
```

`smoke`, `probe`, `voice_smoke`, `voice_probe`, `authoring_eval` and `document_eval` (except `--render-only`) call the real API and cost money. The first four run on chapter files (`--chapter-dir`, default `tests/fixtures/chapters/suites`, except that the drawing probe sets pick their own chapters, see `scripts/probe.py`; `--subject`, default `mathematics`), not the database. Each takes `--language en` (the English fixtures and prompts; `probe` also has `--dry-run`, free). None runs as part of `pytest`. They run on the AI configuration the server would use (spec 014: the environment, then what an administrator stored when `DATABASE_URL` and `SECRETS_DIR` point at a database; `scripts/ai_clients.py`), so `OPENAI_BASE_URL=… OPENAI_MODEL=… uv run python -m scripts.probe` measures any provider, and each prints `provider host · model` first. After changing a board block's schema, run `voice_smoke` as well: the Realtime session receives the same declarations. `smoke` is the fastest way to tell whether a change broke the cached prefix: it exits non-zero if the second turn reports zero cached tokens.

`create_app` is a factory, so uvicorn needs `--factory`. There is no module-level `app`, deliberately: importing one would run startup validation at import time and break the test suite.

Configuration comes from `.env` in `backend/` or at the repository root, read once through `app/config.py`. Both locations are gitignored.

## Layering

Four layers, and the dependency direction is one-way:

```
api/routes   controllers: HTTP, SSE framing, status codes. No business logic.
api/schemas  wire DTOs (request, response, SSE events)
services     prompt library and assembly, the turn loop, tools, history mapping, auth, chapters, the authoring agent and runner
db           SQLAlchemy models, repositories (one short session per call), Alembic migrations
providers    the only place that knows about the SDK and the vendors' wire formats (OpenAI, and any OpenAI-compatible server)
domain       models and errors, depended on by everything, depending on nothing
```

**Nothing above `app/providers/` may import `openai`.** A test enforces it. The turn loop talks to the `LLMClient` protocol in `providers/base.py`, the authoring agent to `CompletionClient`, and the voice routes to the `RealtimeClient` protocol next to them, which is what lets every test run offline against a scripted fake instead of the network. Every client is built by `providers/hub.py` from an `AiConfig` (spec 014: a connection and a model per role, resolved by `services/ai_resolution.py`, environment > stored > default); a service that needs a model name reads it from the hub's current configuration per call, never at construction, and `complete(role=…)` lets the role's client own its model, effort and connection. Chat Completions is a second adapter behind the same protocols (`providers/openai_chat.py`, `chat_translate.py`). `documentation/ai-providers.md`.

## What matters here

- **The turn is stateless; the record is not.** No `previous_response_id`: in the parcours the browser owns the transcript and posts it back whole on every turn, and `store=false` on every provider call so nothing is retained upstream. A **discussion**'s transcript is a `conversations` row instead — the turn names it and the server appends once, when the turn ends (`../documentation/discussion.md`). The database holds users, sessions, courses, chapters (with their pack and curriculum), authoring runs, progress, conversations and the AI usage ledger. Progress is loaded by the controller into the `TurnContext` and written by the section tools through `ctx.commit`, in the same request that emits the event; a failed write is a tool error and no event.
- **Every route declares its roles.** `require_roles(...)` in `api/deps.py` is the only way in; `tests/unit/test_route_guards.py` fails on any route without it. Ownership is checked by `owned_course` / `owned_chapter` in the query (404, never 403); `lesson_chapter` adds `409 chapter_not_ready`. Mutating requests pass the same-origin middleware unless they carry a bearer.
- **Chapters come from the database.** `ChapterRepository.get_owned` loads a chapter with its course; `services/chapters.py` turns it into a `LessonChapter` (subject, pack, parsed curriculum cached per content version). `TutorService` and `VoiceService` take a `LessonChapter`. Every content change goes through one transaction (`adopt_content` / `adopt_authored`): content, version + 1, progress deleted.
- **Authoring runs in the background, in process.** `services/authoring/agent.py` (pack as Markdown, then curriculum as strict JSON, each validated by `domain/pack.py`, `domain/curriculum.py`, `domain/references.py` and repaired a bounded number of times) and `services/authoring/runner.py` (per-student limits from the runs table, a semaphore, a timeout, orphans failed at startup). Tests drive it with `tests/fixtures/fake_completion.py`. See `../documentation/authoring.md`.
- **Uploaded documents never reach the event loop or the disk.** `services/documents.py` renders PDFs and photos to page JPEGs in a `ProcessPoolExecutor` with a timeout (pdfium and Pillow on untrusted bytes), and `api/middleware.py` caps request bodies while they stream (`DOCUMENT_MAX_BYTES` on the two upload routes, `MAX_BODY_BYTES` elsewhere). The pages live only in the run's memory: the transcription stage of the agent (`domain/transcription.py` validates its page markers) writes the text as the chapter's source, and a run that fails before that asks for the document again (`409 document_needed`).
- **The prompt prefix is load-bearing for cost.** The developer message carries the tutor prompt, the subject prompt, the pack and the path overview and a `prompt_cache_breakpoint`, and tool declarations sit in the same cached prefix in a fixed order. Reordering either, or letting anything varying drift in front of the breakpoint, silently multiplies the token bill. `usage.input_tokens_details.cached_tokens` is logged per turn to catch it. Anything that varies per turn (the time, the path state) goes in the trailing developer message, after the transcript.
- **The SSE event set is a two-sided contract** with the frontend. It is specified in `../specs/001-tutor-chat-agent/design.md` §3.2 plus the two section events in `../specs/002-chapter-sections/design.md` §3.2, and pinned by golden transcript tests. Changing it means changing the frontend types and the design document in the same breath.
- **Five tools, fixed order, and a mode decides which are offered.** Two board tools, two section tools, `propose_next_step` — the last is how the tutor hands the learner the « Étape suivante » button instead of pushing the next card itself. `registry.declarations(mode)` gives the parcours all five and a discussion the two board tools, built once per mode so the bytes stay stable; `registry.execute` refuses anything outside the turn's mode, which is what makes the mode a server-side fact when `/api/voice/tool` takes a tool name from the browser.
- **The locked path is enforced in the tools.** `services/path.py` is a pure function of curriculum and progress; `start_section` and `complete_section` refuse through it. The prompt only tells the model that the tool will say no. Do not move those rules into prompt text.
- **Model output is untrusted.** Tool arguments are validated by Pydantic before use; a validation failure is returned to the model as a tool result so it can correct itself, never raised as an HTTP error. `display_board` adds rules Pydantic cannot hold, in this order: the string checks (`string_control`, a JSON escape that ate a LaTeX backslash; `string_latex`, a LaTeX command outside `$…$`; `string_script`, a bare `u_n` or `m·s^-2`), a `definition` not in the pack, at most two drawings per card of any family (`drawing_refused`, rule `per_card`), then one rule module per drawing block, dispatched by the `_FAMILIES` table in `services/tools/board.py`, which also logs `<block>_refused` / `<block>_displayed` (a string check failing inside a drawing is logged under its family):
  - `charts.py` (spec 008);
  - `flowcharts.py`: one flowchart per card, the graph rules, a box whose text only marks a hole (`placeholder`), and hidden boxes whose text shows elsewhere;
  - `figures.py`: geometry that tells the truth, notation the board writes itself however its LaTeX spells it, numbers the board can scale, what fits a diagram of sets;
  - `plots.py`: expressions parsed by `domain/expression.py`, the grammar the board draws with; `pack_function` reads the chapter's pack (`PACK_WORDS`: the pack must name the function, not a word sharing its root; expressions only, so a function drawn from points is not checked); an open exercise's drawing may not show values, relations, coordinates or intervals.

  A card's `drawing` is the `Drawing` union in `domain/board.py`. Its callable discriminator (`_drawing_type`) reads a missing `type` from the drawing's keys (`chart`, `figure`, `nodes`, `x_range`/`y_range`/`curves`) and falls back to a chart (008), so every later drawing block declares `type` as required and one sent without it gets its own block's error. Which strings are prose is marked on the models: a field of raw LaTeX, ids or an expression carries `NOT_PROSE` (`domain/prose.py`), and a `Literal` is never prose; mark a new field of that sort, or the string checks will read it as prose. `$…$` is read by `MATH` in `services/tools/text.py` (JavaScript whitespace, as the board's `RichText`), the one backend copy of the delimiters; `spaced` is there too. Rules that could change live in the tool, not on the card model, so stored cards keep replaying. Why each drawing block is built the way it is: `../specs/009-board-drawings/`.
- **Some rules share a case table with the board.** Where a tool rule depends on how the board lays something out or parses it, both sides read one JSON table, and the frontend keeps a byte-identical copy that a test compares:
  - `tests/fixtures/flowchart_layers.json` ↔ `frontend/src/components/celestin/flowchart/__tests__/layer_cases.json`: the rows `wide` counts;
  - `tests/fixtures/figure/capacity.json` ↔ `figure/__tests__/capacity.json`: what `crowded` lets into a diagram of sets;
  - `tests/fixtures/expression_cases.json` ↔ `plot/__tests__/expression_cases.json`: the plot grammar;
  - `tests/fixtures/accept_language_cases.json` ↔ `frontend/src/lib/__tests__/accept_language_cases.json`: how an `Accept-Language` header becomes `fr` or `en` (spec 010; the page and the API must agree).
  - `tests/fixtures/notation_cases.json` ↔ `frontend/src/components/celestin/charts/__tests__/notation_cases.json`: what the board writes for an interval, a pair and a number in each course language, and that the rule patterns (`INTERVAL`, `COORDS`, `_number`) recognise and read it back (spec 011).

  Change both copies in the same commit, formatted with prettier (the frontend's `npm run format` would otherwise rewrite its copy).
- **Text for the student goes through the catalog; text for the model never does** (spec 010, `../documentation/i18n.md`). `users.locale` (`fr` or `en`) is the account's interface language. An error holds a key and parameters (`TutorError.message(locale)`, no `message_fr`), a tool outcome holds a `Marker` (a str: its French text, plus the key to say it again), a `ContentIssue` has an optional `code`; `app/domain/messages/` (`fr.py`, `en.py`, `render`, `render_issue`) turns them into text at the edge, in the language of the request: `api/locale.py` `locale_of(request)` is the account's (left on `request.state` by `current_user`), else `Accept-Language`. The HTTP handler, the middleware, the SSE stream, the voice routes and the DTOs all do this. What the model reads (`prompts/`, tool outputs and `ToolValidationError` text, history, `curriculum_render`) takes no locale and does not import the catalog; it takes the **course language** (spec 011) instead: `tests/unit/test_model_input_wall.py` enforces it and proves an `fr` and an `en` account on the same course hand the provider identical input, while a French and an English course hand it different input. A new error, status or marker needs a key in both catalogs (`test_messages.py` checks parity). French stays byte-identical: `tests/fixtures/error_messages_fr.json`, `status_messages_fr.json` and `markers_fr.json` were recorded from the code before the catalog existed.
- **The course language is a parameter of everything the model reads** (spec 011, `../documentation/course-language.md`). `courses.language` (`fr` or `en`) reaches `LessonChapter.language` and `TurnContext.language`; the prompt library, `curriculum_render`, the path and tool words, `history`, the tool rules (`PACK_WORDS_BY_LANGUAGE`, `HOLE_WORDS`, `INTERVAL`/`COORDS`/`_number`, `COMMA`), the transcription `MARKERS`, `chapter_title`, `AGENT_WORDS` and `registry.declarations(mode, language)` all take it. Every per-language table is declared with `by_language` (a language missing from a table fails at import), and `tests/unit/test_language_is_passed.py` fails on a call site that does not name the language. French is the default of every parameter and is byte-identical to what it was.
- **Every call to a model is attributed and recorded** (spec 015, `../documentation/ai-usage.md`). `ProviderHub.build` wraps the clients it builds in `providers/recording.py` (`RecordingLLM`, `RecordingCompletion`, `RecordingTranscriber`), which write one `ai_usage` row per call through an injected sink (`UsageRecorder`: off the event loop, never raises; `app/providers/` imports nothing from `app.db`, a test enforces it). *Who* comes from a `UsageScope` in a `contextvar` (`domain/usage.py`): `TutorService.run_turn`, `AuthoringRunner._start` (around `create_task`), `WorkReader.read`, `DictationService.dictate` and the admin test open one; **a call outside a scope is not recorded, and `tests/unit/test_usage_scopes.py` fails on a call site not in its table**. A row is metadata only (`test_privacy_ledger.py` pins the columns and sweeps rows, logs and admin answers for content), and `cost_usd` is the provider's own figure or null: never compute one, never read a `*_PRICE_*` setting for it. `null` tokens mean « not reported » (the Chat adapter's `usage_dict` leaves absent fields out). A voice session is one row written by `/api/voice/usage` (the browser's figures; the course and chapter from `VoiceSessionScopes`). The admin reads it through `api/routes/usage.py` (`AiUsageRepository`: SQL aggregates, `has_more` instead of a count).
- **Voice reuses the text machinery, never re-implements it.** `services/voice_service.py` builds the Realtime session from the same prompt rendering (`voice=True`) and `registry.realtime_declarations()`, and `/api/voice/tool` runs `registry.execute` plus `tool_events.event_of`, the same function the turn loop uses. `/api/voice/session` and `/api/voice/tool` are the two routes that spend money on request; both require the student who owns the chapter (`open_lesson`), and the mint is rate-limited per user (`VoiceBudgetDep`). The authoring routes are the other ones, bounded by the runner's limits. **Dictation** (`POST /api/dictation`, `services/dictation.py`, `providers/openai_transcription.py`) is a third: one recording in, text out, nothing stored or logged; it runs on the voice role's speech model and connection without needing Realtime (`AiConfig.dictation`, `hub.dictation_available`), is rate-limited per user (`DictationBudgetDep`) and size-capped while the body streams (`DICTATION_MAX_BYTES`). See `../documentation/voice.md`. **Photographed work** (`POST /api/courses/{id}/work`, `services/work_reading.py`, `prompts/transcription/work.<lang>.md`) is a fourth: a photo of her handwriting is read by the transcription role into text the student corrects and sends; the tutor never sees the picture, nothing is stored or logged (`../documentation/work-reading.md`).

## Prompts and course content

Everything we write for a model is under `prompts/`, read through `services/prompts.py` (`PromptLibrary`, mtime-cached, checked at startup: a missing or broken file stops the process naming it, and shows in `/api/health` if it breaks later):

- Every file below exists once per course language (`name.fr.md`, `name.en.md`); `tests/unit/test_prompt_files_languages.py` compares each English file with its French twin. The French names are used in the list.
- `tutor.fr.md` — the tutor's instructions, in French, subject-neutral, mode-neutral and gender-neutral. Markers: `<!-- SUBJECT -->` (the subject prompt), `<!-- COURSE_PACK -->` (the chapter's pack), `<!-- CURRICULUM -->` (the overview), `<!-- MODE -->` and `<!-- MODE_OPENING -->` (the mode's two files), plus a `<!-- VOICE -->` … `<!-- /VOICE -->` block only a Realtime session receives.
- `modes/<mode>.fr.md` and `modes/<mode>.opening.fr.md` — how a mode works and how one of its sessions opens. Adding a mode is a value in `domain/mode.py`, these two files and a row in `_MODE_TOOLS`; never a second turn loop.
- `subjects/<subject>.fr.md` — how a subject is taught, written, checked, what is off-topic; its own voice block.
- `templates/<subject>.pack.fr.md` — the pack skeleton: sent to the authoring model, and the source of the headings `index_pack` requires.
- `authoring/pack.fr.md`, `authoring/curriculum.fr.md` — the two authoring stages.

A subject exists in `domain/subject.py`; offering one is its prompt and template files in each language plus `available=True` and the languages in `SubjectInfo.languages`. Editing a voice block does not move the text prefix; editing anything else does, and `test_text_rendering_is_byte_stable` will tell you (regenerate `tests/fixtures/render/system_text_sha.txt`, and `system_text_sha_discussion.txt`, for an intended change). Each mode has its own cached prefix per chapter, so `scripts/smoke.py` checks both. Content formats and path rules: `../documentation/chapters.md`; courses, ownership and the auth layer: `../documentation/accounts-and-courses.md`; authoring: `../documentation/authoring.md`.
