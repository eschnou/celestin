# 014 — Tasks

Phases are testable increments in dependency order. Each ends with a check the user can run. Requirement ids (`R1`…) refer to `requirements.md`, section numbers (`§`) to `design.md`. Tick tasks as they land; record design deviations under the phase's **Verified** line.

Work on `feature/ai-provider-configuration`, branched from `main` (the README, LICENSE, `docker-compose.yml` and `CLAUDE.md` edits already in the working tree are committed first, on their own). Not merged and not pushed until the user says so.

Checks for every phase that touches a side: backend `cd backend && uv run pytest`; frontend `cd frontend && npm run typecheck && npm run lint && npm test`.

Constraints across the epic:

- **OpenAI behaviour does not change** (R4.1, R8.6): same request bodies (golden test, Phase 1), same defaults, same environment variables, a stored 013 key keeps working with no admin action.
- Only `app/providers/` imports `openai` (§2); `test_layering.py` allow-list is updated in the phase that adds a module.
- No log line, response, error, test report or fixture carries an API key (R1.7, NFR 4.3.1). Every phase that handles a key has a `caplog` assertion. **The Groq key given in chat is never written to a file, fixture or commit**: it is passed as an environment variable or typed in the UI for manual runs.
- Between the end of Phase 1 and the end of Phase 2 the old settings section talks to routes that no longer exist; the branch is not pushed in that window.

**Deviations from the design:**

1. `AiConfigSource` lives in `providers/base.py` (not `hub.py`) so services can import it without the hub. `FixedAiConfig` is the static source the tests use (`tests/fixtures/fake_clients.py`; the scripts build a real hub).
2. The resolution logic is its own module, `services/ai_resolution.py` (`Resolver`, the state dataclasses, the stored-document parser); `ai_settings.py` holds the service. Same behaviour as §3.3.
3. `ProviderHub` gains `build(config)` and `install(clients)`: a save builds the clients first (so an unbuildable configuration is refused before anything is written) and installs them last. `apply` is `install(build(…))`.
4. **Streaming uses `responses.create(stream=True)`, not `responses.stream()`** (§3.5 said the adapter kept the SDK helper). The helper folds events into a snapshot and raised `IndexError` on Groq's `qwen/qwen3.8-27b` (an event for an output index it never announced). The request body is identical; the events are the same objects.
5. **`wire_input` does more for non-OpenAI hosts** (§3.5 only stripped `prompt_cache_breakpoint`): the first `developer` message is sent as `system` and every later one as `user`. Qwen's chat template on Groq rejects the `developer` role and a conversation with no user message, and the tutor's opening turn is only the prompt and the path state. OpenAI input is untouched (same objects).
6. The probe decides a model's visibility from the listing first and asks for the model itself only when it is not listed (ids with a slash, such as `openai/gpt-oss-120b`, are not found by a path lookup, so every Groq model read « not available »).
7. An API key's length and shape are judged by the service, not by the request schema: a pydantic refusal echoes the offending input, the key, in the 422 body. Every key refusal is `invalid_ai_settings`.
8. `scripts.smoke` no longer fails on a missing cache hit when the tutor is not on OpenAI (the breakpoint is OpenAI's); it says so and exits 0.
9. Error classes: the three provider subclasses share a mixin (`_SameSentence`) rather than a base class, so each concrete class has one row in `error_messages_fr.json` and the base needs none.
10. `ModelListing` and the settings view are built from service dataclasses (`from_attributes`); the live-check fields exist on `RoleTest` (`live=None`) ahead of Phase 4.

1. **The tutor check uses the application's own five tool declarations and requires a valid `display_board` call** (checked with the tool's Pydantic model through the new `registry.arguments_valid`), not a toy `ping` tool. 2. **A built-in default reasoning effort applies to OpenAI connections only** (§3.3 gave every role today's `medium`/`low` defaults). The settings view shows the effective default (« Par défaut (non envoyé) » on Groq).
3. **`complete()` sent its instructions with the `developer` role to every host** (the earlier `wire_input` rule covered the input only). Fixed: `system` for hosts that are not OpenAI. The live checks caught it.
4. The Groq preset suggests `qwen/qwen3.8-27b` for the tutor and the reader, `openai/gpt-oss-120b` for chapters (§3.10 had `gpt-oss` for the tutor and `qwen3.8` for reading only).
5. Provider text still never reaches the client: a refused request cannot say *which* parameter was refused, so `no_tool_calls` / `schema_unsupported` / `no_image_input` for a refusal are the likeliest cause, not a certainty.
